# Changelog

Проект использует [Semantic Versioning](https://semver.org/lang/ru/). Начиная с 1.0.0
действует полная дисциплина SemVer: обратно несовместимые изменения (схемы хранения,
API сервера лицензирования) требуют мажорной версии; новая функциональность —
минорной; исправления багов — патч-версии.

## [1.9.1] — 2026-08-18 — критичный патч: не работали сообщения content.js → background.js

### Исправлено

**`Uncaught TypeError: Cannot read properties of undefined (reading 'onMessage')` в content.js.**
Content-script "осиротевал", если расширение обновлялось/перезагружалось, пока
страница-SPA (например, `my.selectel.ru`) оставалась открытой — в этом состоянии
`chrome.runtime` становится `undefined`, и регистрация `chrome.runtime.onMessage.addListener(...)`
падала с необработанным исключением. Добавлена ранняя проверка `chrome.runtime.id`
в начале content.js и безопасные обёртки `socCopilotSendMessage`/`socCopilotStorageGet`/
`socCopilotStorageSet`/`socCopilotStorageRemove`, гасящие как этот сценарий, так и
инвалидацию контекста уже после старта скрипта (`chrome.runtime.lastError`,
синхронные исключения при обращении к `chrome.storage.local`).

**Обогащение IOC, LLM-функции (Summary/Predict/Mentor), рассылка в Slack/Telegram/MAX/Teams/Jira,
бейдж, кросс-табовая корреляция были фактически неработающими.** При первом проходе фикса выше
обёртка `socCopilotSendMessage` по ошибке вызывала сама себя вместо `chrome.runtime.sendMessage`
(бесконечная рекурсия, гасившаяся собственным `catch`) — весь канал content.js → background.js
молча не отвечал. Обнаружено и устранено до релиза дополнительным аудитом.

**Redaction (обезличивание перед отправкой в LLM) не покрывал общие секреты.**
`utils/redaction.js` вырезал только SSH/AWS-ключи и JWT; пароли, bearer-токены и
вендорские токены (Stripe `sk_`, GitHub `ghp_`, Slack `xox*`) могли уйти в LLM в
открытом виде. Добавлены паттерны на `password/secret/token/api key: ...`, `Bearer ...`
и токены популярных вендоров.

**XSS defense-in-depth: `href` в панели.** В блоках техник MITRE, прогнозов, похожих
инцидентов и ссылок DFIR-инструментов URL вставлялся в атрибут `href` без экранирования
(`escapeAttr`), в отличие от остального текста. Сегодня не эксплуатируется (браузер сам
percent-encode'ит спецсимволы в URL), но исправлено для консистентности с остальным кодом.

**background.js: сообщения не проверяли отправителя.** `chrome.runtime.onMessage`
теперь явно отклоняет сообщения не от своего расширения (`sender.id !== chrome.runtime.id`).
Сегодня не эксплуатируется (`externally_connectable` не объявлен), это защита от регрессии.

**Гонка при генерации Device ID.** `getOrCreateDeviceId()` в background.js мог
сгенерировать разные UUID при параллельных вызовах на холодном старте service worker —
теперь промис первого вызова кэшируется и переиспользуется.

### Известные ограничения (не исправлено в этом релизе, не блокирует релиз)

- `enrichCache` и `openIncidentTabs` в background.js хранятся только в памяти service
  worker'а и сбрасываются при его выгрузке Chrome (~30 сек простоя) — TTL кэша обогащения
  и кросс-табовая корреляция фактически ограничены временем жизни SW. Кандидат на перенос
  в `chrome.storage.session` в одном из следующих релизов.
- `migrateSecretsToEncrypted()`/`applyManagedPolicies()` могут в редких случаях выполниться
  параллельно из `onInstalled` и `onStartup` — идемпотентно, но с лишними операциями.

## [1.9.0] — 2026-08-18 — критичный патч: CSP блокировала тестовый стенд SIEM; выбор логотипа

### Исправлено

**Тестовый стенд SIEM (test-siem.html) не отображал данные.** Chrome блокировал
инлайновый `<script>` со сценариями (SCENARIOS/render) ошибкой CSP:
"Executing inline script violates the following Content Security Policy directive
'script-src 'self''...". Причина: MV3 по умолчанию задаёт для страниц расширения
`script-src 'self'` без `'unsafe-inline'`, а test-siem.html открывается именно как
страница расширения (`chrome.runtime.getURL("test-siem.html")` из popup.js) — поэтому
эта CSP на неё и распространяется. Инлайновый скрипт никогда не выполнялся, элементы
карточки инцидента (#bt-title, #bt-description и т.д.) так и оставались в состоянии
"Загрузка…", а кнопки переключения сценариев не отвечали.

Исправлено: сценарный код вынесен во внешний файл `test-siem.js`, подключаемый
как `<script src="test-siem.js"></script>` — CSP `'self'` его разрешает. Файл добавлен
в `web_accessible_resources` манифеста.

**Тот же класс бага** — на странице настроек (options.html) инлайновый `<script>`,
подставлявший номер версии в блок "О программе" (#about-version), тоже блокировался
CSP и молча не срабатывал. Перенесён в options.js.

### Добавлено

- **Выбор логотипа плагина.** В разделе «Оформление и язык» страницы настроек — селектор
  «Логотип плагина»: «Вариант 1» (стандартный, `icons/*.png`) и «Вариант 2» — набор,
  который администратор кладёт самостоятельно в `icons/logo2/` (icon16/48/128.png,
  см. `icons/logo2/PLACE_LOGO_HERE.txt`). Применяется к иконке расширения в панели
  инструментов через `chrome.action.setIcon()` сразу после сохранения и при каждом
  запуске браузера/установке. Если файлы варианта отсутствуют — сохранение блокируется
  с предупреждением и текущая иконка не меняется (проверка через HEAD-запрос к
  `chrome.runtime.getURL(...)` перед применением).

## [1.5.1] — 2026-08-15 — критичный патч: расширение не устанавливалось в Yandex Browser

### Исправлено

**Расширение не загружалось вовсе** — сообщено пользователем при попытке установки в
Yandex Browser: `Invalid type for attribute 'additionalProperties'. Не удалось
загрузить манифест.` Причина — `schema.json` (используется для enterprise-политик
через `"storage": {"managed_schema": "schema.json"}` в манифесте, см. 0.9.0) содержал
`"additionalProperties": false` на верхнем уровне. Это валидный JSON Schema, но
Chromium-парсер политик расширений (используется и в Yandex Browser, и в Chrome/Edge)
работает не по полному JSON Schema, а по собственному ограниченному формату policy
schema, где `additionalProperties`, если указан, ожидается как объект-схема
(описывающий тип разрешённых дополнительных свойств), а не как булево значение —
булево значение вызывает ошибку типа при парсинге, а не молча игнорируется.

**Исправлено**: строка `"additionalProperties": false` удалена из `schema.json`.
Функциональность не теряется — без этой строки дополнительные (не описанные в схеме)
свойства политики просто разрешены по умолчанию, чего было достаточно и раньше,
поскольку строгий запрет на них не был частью функциональных требований, только
побочным эффектом добавления строки без проверки на реальных Chromium-браузерах.

### Что это означает для 0.9.0–1.5.0

Если расширение НЕ устанавливалось у вас (ошибка на этапе загрузки манифеста, ещё до
первого запуска) — вы не пострадали от этого бага никаким другим образом, кроме самой
невозможности установки; функциональность после исправления идентична предыдущим
версиям, просто теперь расширение реально загружается в Chromium-браузерах со строгой
валидацией policy-схем (подтверждено сообщением пользователя именно для Yandex
Browser — вероятно, воспроизводилось бы и в актуальных версиях Chrome/Edge с той же
строгой проверкой, а не является особенностью только Yandex Browser).

### Урок для процесса

Ни один из предыдущих комплексных security-аудитов (включая v1.5.0) не поймал эту
проблему, потому что `schema.json` проверялся только на валидность как JSON
(`python3 -m json.tool` — синтаксически файл полностью корректен) и на использование
в манифесте, но не на соответствие специфичному, более узкому подмножеству,
которое реально принимает Chromium policy schema parser — валидный JSON и валидная
policy-схема для расширений Chrome — не одно и то же, и это не проверялось вживую ни
в одном браузере до сообщения пользователя. Внесено как явный пробел в процесс
проверки на будущее.

извлекало текст (`h1,h2` / `main,body`), запускало IOC-детектор, писало событие в
ПОСТОЯННОЕ хранилище (`eventsLog`) и регистрировало вкладку для кросс-корреляции —
**на каждом посещаемом сайте**, а не только на карточках инцидентов SIEM. Это прямо
противоречило принципу «активируется только на распознанных платформах»,
заявленному в README с версии 0.1.0.
**Исправлено:** `enabled: false` по умолчанию (`adapters.js`) — включение теперь
осознанное действие аналитика, с явным предупреждением в `options.html` о
последствиях (сайт-агностичная активация).

### 🟡 Средние находки — исправлено

- **CORS (`Access-Control-Allow-Origin: *`) применялся одинаково ко всем
  эндпоинтам сервера лицензирования, включая `/api/admin/*`.** Админ-эндпоинты по
  дизайну вызываются только с CLI/curl — легитимного браузерного клиента у них нет,
  разрешать к ним CORS не даёт пользы, но увеличивает поверхность атаки при
  гипотетической утечке `ADMIN_API_KEY`. `sendJSON()` теперь принимает
  `{ allowCors: false }`, применено ко всем 3 admin-обработчикам и к preflight
  `OPTIONS` для `/api/admin/*`.
- **При реализации этого же фикса сам внёс regression-баг**: `pathname`
  использовался в обработчике `OPTIONS` до его вычисления (temporal dead zone для
  `const`) — уронило бы сервер `ReferenceError`'ом на каждый OPTIONS-запрос.
  Пойман немедленным regression-тестом сразу после фикса, до продолжения работы.
  Вычисление `url`/`pathname` перенесено в начало обработчика запроса.
- **`toggleMarketplacePreview()` в `options.js`** интерполировала `id` в
  CSS-селектор атрибута без `try/catch`, в отличие от аналогичных мест в
  `content.js`. Сервер уже валидирует `id` строго regex'ом
  (`^[a-zA-Z0-9_-]{1,64}$`), так что практической эксплуатации не было — фикс
  добавлен для defense-in-depth и консистентности с остальным кодом, а не потому,
  что нашлась реальная дыра.

### 🔍 Проверено детально, включая опровергнутую гипотезу

При первом проходе аудита возникло подозрение на **stored XSS через маркетплейс
адаптеров** — что поля `name`/`vendor`/`id` устанавливаемого чужого адаптера могли
попадать в `innerHTML` страницы настроек без экранирования. При точной построчной
перепроверке всех связанных функций (`renderAdapters()`, `populateMarketplacePublishSelect()`,
рендер списка маркетплейса) подозрение **не подтвердилось** — `escapeHtml()`
применяется во всех точках, включая атрибутные контексты (`value="..."`). Не стал
публиковать неточную запись о найденной уязвимости только потому, что она была
предположением на промежуточном этапе — здесь фиксируется то, что действительно
проверено и актуально для текущего состояния кода.

Дальнейшая систематическая проверка (без предварительных подозрений, по всей
кодовой базе):
- **XSS через `innerHTML`**: построена полная карта всех точек `innerHTML` в
  проекте. Особое внимание — данным от МАРКЕТПЛЕЙСА и ГЛОССАРИЯ, единственным
  источникам контента от посторонних организаций в системе: везде подтверждено
  `escapeHtml()`/`escapeAttr()`. Поля карточки инцидента SIEM (`title`,
  `description` и т.д. — потенциально содержат текст, вставленный атакующим,
  например тема фишингового письма) — единственная HTML-точка вставки (вкладка
  «Сводка») корректно экранирована; остальные использования — JSON-хранилище или
  простой текст для внешних мессенджеров, не HTML-контекст.
- **`eval()`, `new Function()`, `document.write`, `.outerHTML`** — не используются
  нигде в проекте.
- **ReDoS** (катастрофический backtracking в regex): все паттерны
  `ioc-extractor.js` и `redaction.js` (16 паттернов, включая SSH-ключи с
  `[\s\S]*?`) прогнаны на входе 50 000 символов без совпадения в конце — везде
  &lt;5мс, включая отдельный тест незакрытого PGP-блока на 100 000 символов.
- **Прототипное загрязнение** через `__proto__` в JSON-теле запросов к серверу —
  все обработчики используют явную деструктуризацию именованных полей, а не
  `Object.assign`/спред всего тела.
- **Rate limiting** на эндпоинтах маркетплейса/глоссария подтверждён покрытым —
  `marketplace-publish`, `marketplace-download`, `glossary-submit`,
  `glossary-vote` лимитированы по IP.
- **Логирование секретов**: грепом по всей серверной кодовой базе подтверждено
  отсутствие `console.log` с ключами/токенами/паролями.
- **Константное сравнение** (`crypto.timingSafeEqual`) для `ADMIN_API_KEY`
  повторно подтверждено, не задето правками этого релиза.
- Полный регрессионный тест всех подсистем сервера (лицензии → активация →
  маркетплейс → глоссарий → ingest → метрики → health) после всех фиксов — при
  первом прогоне тест сообщил об ошибке активации; расследовано немедленно,
  оказалось ошибкой в самом тесте (deviceId короче минимальной длины 4 символа),
  не багом кода — подтверждено повторным тестом с корректным deviceId.

### Известные ограничения после этого аудита

- Аудит — ручной систематический обзор с точечными автоматизированными тестами
  (ReDoS-таймингы, сквозные HTTP-сценарии), не формальный penetration test и не
  автоматическое SAST/DAST сканирование. Для окружений с повышенными требованиями
  (КИИ, финансовый сектор) рекомендуется независимый внешний аудит перед
  продакшен-развёртыванием.
- Экспертный контент «советующих» модулей (Sigma/YARA-черновики, DFIR/СЗИ-
  рекомендации) не проверялся на предметную корректность в рамках ЭТОГО аудита —
  это security-, а не domain-проверка; см. соответствующие релизы за оговорками о
  черновом характере рекомендаций.

  Română). Переключатель в настройках.

### Честно про объём мультиязычности (не скрыто, написано прямо в UI настроек)
Переведена интерфейсная «оболочка» — заголовок панели, названия 8 вкладок, общие
кнопки (копировать/проверить/закрыть) — самая заметная часть UI. Динамический контент
(шаги наставника L1-L3, описания DFIR-инструментов, тексты плейбуков, сгенерированные
отчёты/заключения — многие тысячи слов) остаётся на русском. Полный перевод ВСЕГО
контента на 30 языков — отдельный по объёму проект локализации, а не одна функция;
попытка сделать это наспех дала бы либо низкое качество перевода, либо непропорционально
большую часть релиза на одну фичу в ущерб остальным. Список переведённых ключей и языков
проверен программно на полноту (30×20 = 600 переводов, ни одного пропуска).

### Архитектурное решение (темы)
- Класс темы применяется на `shadowHost` (элемент в light DOM, владелец shadow root), а
  переопределения переменных используют селектор `:host(.sc-theme-X)` — так стили
  корректно каскадируются во ВСЁ shadow-дерево, включая кнопку-тумблер `.sc-toggle`,
  которая лежит вне `.sc-panel` как отдельный узел. Применение класса напрямую на
  `.sc-panel` не сработало бы для тумблера — до этого поведения дошли до правки, а не
  после (проверено до, а не постфактум).

### Проверено перед сборкой
- Полнота словаря переводов: 30 языков × 20 ключей, ноль пропусков (программная проверка).
- Баланс фигурных скобок CSS после массовой замены цветов на переменные — не нарушен.
- Полный аудит (синтаксис/дубли функций/HTML id/сверка message-типов) — как перед
  каждым релизом, расхождений не найдено.
- Отображение всех 8 вкладок панели протестировано на 6 языках разных языковых семей
  (кириллица, латиница, иероглифы, письмо справа-налево, деванагари) — рендерится
  корректно на уровне текста (визуальная проверка в реальном браузере не проводилась,
  т.к. песочница без GUI — рекомендуется ручная проверка RTL-языков (арабский, урду,
  персидский) на реальной установке, направление текста в CSS не задавалось явно).

### Известные ограничения нового релиза
- RTL-языки (арабский, урду, персидский) переведены лексически, но CSS не переключает
  направление панели на `dir="rtl"` — текст будет читаться в верном порядке слов, но
  общая раскладка панели (кнопки слева/справа) останется LTR. Это визуальный, не

- Высокий контраст — базовый уровень (цвета, границы), не полный аудит на соответствие
  конкретному стандарту (WCAG 2.1 AA/AAA) со всеми контрастными соотношениями.

  смысл маркетплейса. Новые серверные эндпоинты: `GET/POST /api/marketplace/adapters`,
  `POST /api/marketplace/adapters/:id/download`.

### Архитектурное решение (маркетплейс)
- Лицензионный ключ, необходимый для авторизации запросов к маркетплейсу,
  расшифровывается **исключительно** в `background.js` — `options.js` передаёт только
  нечувствительные данные адаптера (id/название/селекторы, не секрет), а авторизацию
  к серверу background.js добавляет сам. Тот же принцип write-only/decrypt-only-in-
  background, что и для остальных секретов с версии 0.9.0.

### Исправлено / безопасность (аудит перед сборкой)
- При первой реализации серверных обработчиков публикации/скачивания адаптеров
  авторизация проверялась ОТДЕЛЬНЫМ вызовом `loadDB()` до вызова `withDB()` для
  мутации — двойное чтение БД создавало мелкую гонку (TOCTOU) между проверкой
  лицензии и записью, не соответствуя уже устоявшемуся в остальном коде паттерну
  (проверка и мутация в одном `withDB()`). Переписано на единый паттерн, консистентно
  с `handleActivateOrValidate`.
- Полный сквозной тест маркетплейса (7 сценариев: публикация → конфликт id между
  организациями → запрет без авторизации → листинг → скачивание со счётчиком →
  повторная проверка счётчика → валидация некорректного id) — все прошли на реально
  запущенном сервере до сборки релиза.
- Обнаружен и исправлен пробел: `populateMarketplacePublishSelect()` была объявлена,
  но не вызывалась после загрузки локальных адаптеров — выпадающий список публикации
  оставался бы пустым. Добавлен вызов в `loadAdapters()`.
- Полная сверка всех типов сообщений `content.js`/`options.js` ↔ `background.js`
  после добавления 3 новых обработчиков маркетплейса — расхождений нет.

### Осознанно всё ещё отложено
- Shadow-режим для сеньоров (read-only подписка на поток L1 с автоматическим QA) —
  сложная модель прав доступа, требует отдельного продуманного дизайна.

  модерации, которой пока нет ни на сервере, ни в расширении.

### Известные ограничения нового релиза
- Шифрование в расширении защищает от казуального/автоматизированного чтения

### Добавлено — счётчики и отчёты
- Новая вкладка «📊 Статистика» в панели. Чёткие определения счётчиков (важно для доверия
  к цифрам): **«событие»** = уникальная карточка, которую плагин распознал (по URL);
  **«инцидент»** = карточка, по которой аналитик СОХРАНИЛ заключение — так счётчик отражает

  статистики по всей команде SOC.

### Добавлено — геймификация BelZor
- Новая валюта поощрения **BelZor** (Беляев + зоркость/внимательность) начисляется при
  сохранении заключения по инциденту. База зависит от критичности (парсится из текста поля
  критичности карточки на русском/английском, с fallback на эвристический риск-скор, если
  поле не удалось разобрать): Critical — 50, High — 30, Medium — 15, Low — 5.
- Бонусы за индикаторы качественной работы (не за «правильность» вердикта — плагин не может
  её проверить): +5 за использование контекста MITRE ATT&CK, +5 за полное прохождение
  плейбука, +10 за фактическую проверку хотя бы одного IOC через TI-сервис.
- Система рангов: Новобранец → Внимательный (100) → Бдительный (300) → Страж/BelZor Guardian
  (700) → Мастер реагирования (1500). Уведомление о повышении ранга — тост в панели.
- Защита от повторного начисления: BelZor начисляется один раз за конкретную карточку
  (по URL), даже если заключение пересохраняется несколько раз.
- Баланс и ранг видны в popup без открытия панели.

### Аудит перед релизом
- Полная проверка на дубли объявлений функций во всех JS-файлах — не найдено.
- Проверено соответствие `data-tab`/`data-tab-content` для всех 8 вкладок панели (включая
  новую «Статистика») — 1:1, «мёртвых» вкладок нет.
- Сквозной тест агрегации статистики по всем 5 периодам на синтетических данных с разными
  датами — скользящие окна корректно включают/исключают записи на границах.
- Сквозной тест начисления BelZor с переходом ранга (Новобранец → Внимательный) —
  корректный расчёт базы, бонусов и определение момента повышения ранга.
- Проверена защита от двойного начисления BelZor при повторном сохранении заключения по
  той же карточке.

### Известные ограничения нового релиза
- Периоды отчёта — скользящие окна в днях, не привязаны к календарным границам месяца/
  квартала/года (например «месяц» — это 30 последних дней, а не текущий календарный месяц).
- Определение критичности из текста поля — эвристика (ключевые слова на рус/англ), как и
  везде в парсере; при нестандартных формулировках сработает fallback по риск-скору.
- BelZor поощряет тщательность процесса (использование MITRE, полный плейбук, проверку
  через TI), а НЕ фактическую правильность вердикта — плагин не может это проверить
  автоматически, и не должен интерпретироваться как оценка качества работы аналитика для
  HR-целей без понимания этого ограничения.

- **Мини-квизы на реальных данных**: например «определи тип этого индикатора» с настоящим
  IOC из карточки, «какая тактика ATT&CK уже пройдена» по реально обнаруженным техникам —
  не банк случайных вопросов, а привязка к конкретному разбираемому инциденту.
- **Socratic-диалог с AI-наставником**: свободный вопрос аналитика по инциденту — модель
  по умолчанию отвечает наводящими вопросами, поощряя самостоятельное рассуждение, а не сразу
  выдаёт готовый вердикт (если аналитик явно просит прямой ответ — даёт его).
- Прогресс сохраняется локально и виден в popup без открытия карточки.
- Обезличивание данных (см. 0.5.0) применяется и к вопросам наставнику — тот же пайплайн,
  без исключений.
